======================================================================
1. PROJECT OVERVIEW
======================================================================

CloudX is a local-first private cloud runtime that allows developers to
deploy, schedule, execute, monitor, recover, scale, and manage services
and jobs across one or more machines.

CloudX provides the orchestration layer normally expected from a cloud
platform while remaining lightweight, developer-focused, local-first,
and understandable.

CloudX should allow a developer to turn a collection of machines into
a small private compute environment.

Example:

Machine A
├── CloudX Control Plane
└── Worker

Machine B
└── Worker

Machine C
└── Worker


A developer can then deploy:

API
Worker
Frontend
Database
Migration Job

and CloudX determines:

- Where workloads should run.
- How many replicas should exist.
- Whether workloads are healthy.
- What happens when a process crashes.
- What happens when a worker disappears.
- How workloads should be rescheduled.
- How versions should be deployed.
- How deployments should be rolled back.
- How services discover each other.
- How resources should be allocated.
- How cluster events should be recorded.

      ↓
CONTROL PLANE
      ↓
SCHEDULER
      ↓
WORKER
      ↓
RUNTIME
      ↓
ACTUAL STATE
      ↓
RECONCILIATION
      ↓
DESIRED STATE


Example:

Developer specifies:

api:
  replicas: 3

CloudX stores:

DESIRED:
3 replicas

Current cluster:

ACTUAL:
2 replicas

CloudX detects:

DESIRED != ACTUAL

The reconciler asks the scheduler for another worker.

Scheduler selects a suitable worker.

Worker receives the task.

Worker starts the process.

Worker reports:

RUNNING

Health manager verifies:

HEALTHY

Actual state becomes:

3 replicas

CloudX has converged to the desired state.

4. WHAT CLOUDX IS NOT
======================================================================

CloudX is NOT:

1. Docker with another CLI.

2. A Kubernetes replacement.

3. A Kubernetes-compatible implementation.

4. A cloud provider emulator.

5. A complete container runtime.

6. A Linux kernel isolation system.

7. A distributed database.

8. An S3-compatible object store.

9. A complete service mesh.

10. A full cloud networking implementation.

11. A cloud-provider-specific platform.

12. An AI-first orchestration system.

13. A dashboard-first product.

CloudX should use existing infrastructure primitives where appropriate,
but its orchestration logic must remain CloudX-owned.

8. CONTROL PLANE
======================================================================

The control plane is the brain of CloudX.

Responsibilities:

- Maintain desired state.
- Maintain cluster state.
- Track workers.
- Track workloads.
- Schedule tasks.
- Reconcile desired vs actual state.
- Manage deployments.
- Manage health.
- Maintain service registry.
- Persist events.
- Coordinate failure recovery.

Major components:

ControlPlane
├── API Server
├── State Manager
├── Scheduler
├── Registry
├── Reconciler
├── Deployment Manager
├── Health Manager
└── Event Manager


======================================================================
9. WORKER
======================================================================

The worker is the execution agent running on a machine.

Responsibilities:

- Register with control plane.
- Send heartbeats.
- Receive task assignments.
- Execute workloads.
- Monitor processes.
- Report task state.
- Report resource usage.
- Perform health checks where applicable.
- Collect logs.
- Report failures.
- Gracefully stop workloads.

Worker architecture:


cloudx-worker

├── Registration Manager
├── Heartbeat Manager
├── Task Manager
├── Runtime Manager
├── Resource Monitor
├── Health Manager
├── Log Collector
├── Volume Manager
└── Event Reporter

11. DESIRED STATE
======================================================================

Desired state describes what the developer wants CloudX to maintain.

Example:

Service:

api

Desired:

replicas = 3
version = v2
cpu = 1
memory = 512MB

Desired state must be persistent.

The system must be able to reconstruct desired state after a
control-plane restart.


======================================================================
12. ACTUAL STATE
======================================================================

Actual state describes what is currently happening.

Example:

api

Task 1:
worker-a
RUNNING
HEALTHY

Task 2:
worker-b
RUNNING
HEALTHY

Task 3:
worker-c
FAILED


Desired:

3

Actual healthy:

2


The reconciler detects the difference.


======================================================================
13. RECONCILIATION
======================================================================

Reconciliation is the central control mechanism.

Concept:

desired state != actual state

must result in corrective action.

Examples:


DESIRED:
3 replicas

ACTUAL:
2 replicas

ACTION:
Create task.


DESIRED:
3 replicas

ACTUAL:
4 replicas

ACTION:
Remove task.


WORKER:
LOST

ACTION:
Identify orphaned tasks and reschedule.


HEALTH:
UNHEALTHY

ACTION:
Restart/reschedule according to policy.


Reconciliation must be:

- Idempotent.
- Deterministic where possible.
- Safe to repeat.
- Failure-aware.
- Persistent-state driven.


======================================================================
14. SCHEDULER
======================================================================

The scheduler determines where workloads should run.

Initial scheduling inputs:

- CPU requirements.
- Memory requirements.
- Worker capacity.
- Worker health.
- Runtime capability.
- Volume locality.
- Node state.
- Affinity.
- Anti-affinity.
- Priority.

Initial algorithm:

1. Discover available workers.
2. Remove unhealthy workers.
3. Remove draining workers.
4. Check resource capacity.
5. Check runtime compatibility.
6. Check volume constraints.
7. Calculate score.
8. Select highest score.
9. Break ties deterministically.

The scheduler must initially remain explainable.

CloudX should be able to explain:

"Why was this task scheduled on worker-2?"

15. RESOURCE MODEL
======================================================================

CloudX initially manages:

CPU
Memory


For every worker:

capacity
reserved
available


For every task:

requested
allocated


The scheduler must not schedule a workload if sufficient resources
are unavailable unless an explicit future overcommit policy allows it.

======================================================================
21. FAILURE DETECTION
======================================================================

CloudX must detect:

- Process crashes.
- Health check failures.
- Worker failures.
- RPC failures.
- Lost tasks.
- Resource pressure.
- Deployment failures.


Worker failure detection uses heartbeats.

Example:

heartbeat interval = 5 seconds

failure timeout = configurable


A single missed heartbeat must not necessarily mean the worker is dead.

The system should tolerate temporary communication delays.


======================================================================
22. FAILURE RECOVERY
======================================================================

Failure recovery is a core CloudX feature.

Scenario:

Worker B hosts:

api-task-3


Worker B disappears.

CloudX:

1. Detects heartbeat timeout.
2. Marks worker B LOST.
3. Finds tasks assigned to worker B.
4. Marks tasks LOST/ORPHANED.
5. Reconciles service desired state.
6. Scheduler selects another worker.
7. Replacement task starts.
8. Health check succeeds.
9. Service returns to desired replica count.

57. CONCURRENCY MODEL
======================================================================

CloudX is a concurrent system.

Important concurrent operations include:

- Heartbeats.
- Reconciliation.
- Scheduling.
- RPC handling.
- Process monitoring.
- Health checks.
- Event processing.
- Resource sampling.
- Log collection.


Use Go concurrency primitives carefully.

Rules:

- Avoid unnecessary shared mutable state.
- Prefer ownership boundaries.
- Protect shared state.
- Use contexts for cancellation.
- Avoid goroutine leaks.
- Ensure graceful shutdown.


======================================================================
58. GRACEFUL SHUTDOWN
======================================================================

Control plane and workers must support graceful shutdown.

Shutdown should:

1. Stop accepting new work.
2. Cancel background loops.
3. Finish safe in-flight operations.
4. Close RPC servers.
5. Close database.
6. Stop managed processes according to policy.
7. Flush logs/events where applicable.
8. Exit cleanly.

======================================================================

- Structured.
- Classifiable.
- Wrapped with context.
- Logged appropriately.
- Safe for user display.

60. SECURITY MODEL
======================================================================

Security principles:

- Authenticate workers.
- Validate all external input.
- Never trust worker-provided state blindly.
- Protect cluster credentials.
- Redact secrets.
- Validate filesystem paths.
- Prevent path traversal.
- Validate command configuration.
- Avoid secret leakage through events/logs.
- Secure RPC communication where configured.


======================================================================
61. PROCESS EXECUTION SECURITY
======================================================================

Native runtime executes developer-defined commands.

Therefore CloudX must clearly document that native execution has the
same privileges as the CloudX worker process.

CloudX should not pretend that the native runtime provides container-
level isolation.

A future container runtime may provide stronger isolation.

CLOUDX INTELLIGENCE

1. Memory usage increased.
2. Health checks began timing out.

Worker resource pressure was elevated during the same period."


AI explains evidence.

AI does not secretly control infrastructure decisions.

75. DEVELOPMENT PRINCIPLES
======================================================================

2. Keep interfaces narrow.

3. Avoid premature abstractions.

5. Keep storage independent of business logic.
